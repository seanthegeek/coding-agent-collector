## 3. Credentials

- `~/.ollama/id_ed25519` is the only credential: Ollama cloud "sign-in" binds this public key to the account ([`app/auth/connect.go:14-25`](https://github.com/ollama/ollama/blob/b0c1ca4f7549d7acdfa52a7dcffc934bc63a43ce/app/auth/connect.go#L14-L25), [`cmd/cmd.go:1012-1026`](https://github.com/ollama/ollama/blob/b0c1ca4f7549d7acdfa52a7dcffc934bc63a43ce/cmd/cmd.go#L1012-L1026)); no token file is written. `id_ed25519.pub` identifies the device.
- No keychain use anywhere in the tree (grep `keychain|Keychain` in cmd, auth, server, app: none).
- `~/.ollama/config.json`, `server.json`, `~/.ollama/backup/*` can contain copies of other tools' settings files (which may embed API keys) but hold no Ollama secret themselves.
- `db.sqlite` `users` table holds account name/email/plan; `attachments.data` holds user-uploaded files.
- `ollama launch chatgpt` creates `~/.codex/auth.json` when none exists, holding the fixed sentinel `{"OPENAI_API_KEY": "ollama-local-codex", "auth_mode": "apikey"}`, which is not an OpenAI credential (section 5). The existing `.codex/auth.json` secret glob flags it like a real one.

## 4. Exclusions

- `.ollama/models/blobs`: model weights (multi-GB `sha256-<digest>` files), the transient `.ollama-split-*` hard-link directories, and any `/save`d REPL session layer, see [`analyzer/research/ollama.md`](../../analyzer/research/ollama.md) section 2 ([`manifest/paths.go:52-72`](https://github.com/ollama/ollama/blob/b0c1ca4f7549d7acdfa52a7dcffc934bc63a43ce/manifest/paths.go#L52-L72), [`llm/model_split.go:21-23`](https://github.com/ollama/ollama/blob/b0c1ca4f7549d7acdfa52a7dcffc934bc63a43ce/llm/model_split.go#L21-L23)). Collector 1.8.1 and earlier excluded the whole `.ollama/models`; the rest of `models/` is now collected: `manifests/<host>/<namespace>/<model>/<tag>`, small JSON files whose names and pre-copy times are an inventory of the pulled models and when each tag was pulled, and `metadata/*.json`, one small file per blob (section 2). No other subdirectory of `models/` is written.
- `AppData/Local/Ollama/updates`, `Library/Caches/ollama`, `Library/Caches/com.electron.ollama`. `Library/WebKit/com.electron.ollama` is outside every catalog line, so it needs no exclusion.
- Docker volumes: the volume-relative exclusion `models` stays whole. It also covers `models` in Tabby (`TABBY_ROOT=/data`), Hermes and Local Deep Research volumes, where it holds model weights or embedding models, so narrowing it to `models/blobs` would collect those. A Docker Ollama volume's `models/manifests` is therefore not collected; [`docs/coverage.md`](../docs/coverage.md) says so.

## 7. Confidence

High: everything in sections 2-5 (source with line numbers, local layout confirmed). Medium: WAL sidecar presence depends on app state at collection. Not determined: whether the macOS app also writes `db.sqlite` into `~/.ollama` on non-standard installs (code says no); size of `~/.ollama/launch/*` and `repl` artifacts of other `ollama launch` integrations.

Resolved, from the collector code: the systemd service home `/usr/share/ollama` is enumerated by the sh collector without an extra root. `enumerate_users` in `collect-agent-artifacts.sh` takes every home from `getent passwd` (or `/etc/passwd` without `getent`) on a live host, or from `<root>/etc/passwd` in image mode, and `filter_users` drops only the listed system paths (`/`, `/usr`, `/bin`, `/nonexistent`, ...), not `/usr/share/*`. The account is created with that home by the installer (section 2), so `/usr/share/ollama/.ollama` is collected as the `ollama` user's home; `collectors/tests/smoke.sh` checks it with a passwd-only home, and a live, non-root collection on this workstation (L, Ollama 0.35.1 systemd install) listed `/usr/share/ollama/.ollama` under the user `ollama`, with `error_copy` rows for the files only that account can read. The PowerShell collector does not read `etc/passwd` in image mode, so on a Linux image it misses that home, as [`docs/coverage.md`](../docs/coverage.md) records under "Home directories"; collect a Linux image with the sh collector.
